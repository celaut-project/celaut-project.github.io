# *Celaut*:一种用于软件设计与分发的点对点架构

<br>

**背景**

20 世纪 40 年代,数学家约翰·冯·诺依曼与斯坦尼斯拉夫·乌拉姆合作,提出了元胞自动机的概念,创建出能够展示简单规则如何催生复杂行为的模型。在此基础上,1970 年约翰·霍顿·康威提出了「生命游戏」,这个元胞自动机成为经典范例,展示了一个系统如何仅凭基础的相互作用演化出错综复杂的模式。这些思想为去中心化系统如何在没有中心控制的情况下实现复杂性提供了宝贵的洞见,这也是 *Celaut* 设计所秉持的指导哲学。

**定义**

*Celaut* 是一套用于软件设计与分发的简单规则,旨在通过**去中心化**、**简洁性**与**确定性**这三项原则,构建一个稳健、可扩展、能够自适应的系统。

**原则**

1. **去中心化**:没有单一的控制点或故障点,让节点能够动态地通信与协调。
2. **简洁性**:极简的规则降低了复杂度,确保每个组件都能被轻松理解和维护。
3. **确定性**:服务的行为是可预测的,遵循既定规则,确保结果在不同节点之间可复现。

***Celaut* 架构:节点与服务**

*Celaut* 的架构围绕两个核心元素构建:**节点**与**服务**。二者共同构成一个分布式网络,其中每一部分都为整体功能做出贡献,就像元胞自动机中的各个单元一样。

- **节点**:
    一个节点代表 *Celaut* 网络中的一台计算机或设备,它能够与其他节点通信,并管理服务的执行。*Celaut* 的去中心化特性,正体现在节点之间的互动方式上,确保没有单一故障点或中心化控制。节点的关键职责包括:

    1. **服务执行**:节点管理服务实例,决定是在本地运行它们,还是把负载分摊到对等节点上。这确保了资源利用与性能的最优化,就像元胞自动机中的单元通过与邻居互动来维持系统平衡一样。

    2. **通信接口**:一个健壮的接口确保节点与服务之间数据交换的顺畅,从而实现有效的协调。值得注意的是,节点无需事先就某个具体的通信协议达成一致,因为这个接口抽象掉了这些细节,从而让交互保持灵活性。这一特性会在下文详细说明。

    3. **地址与令牌供给**:节点通过管理通信地址与身份验证令牌来促成安全的交互,让服务在保持安全的同时也易于访问。

    4. **依赖管理**:节点确保服务能够访问它们所需的依赖项。这些依赖项通常被称为「子服务」,可以运行在同一个节点上,也可以运行在不同的节点上。这项特性让一个父服务能够访问并协调它的子服务,即便服务分布在整个网络中,也能确保一个流畅高效的服务生态系统。

    一个使用 Python3 与 Rust 实现节点的示例是 **Nodo**,详见[这里](https://github.com/*Celaut*-project/nodo)。

- **服务**:
    *Celaut* 中的一个服务,是为执行某个具体任务而设计的确定性软件容器。遵循**黑盒**原则,服务独立于执行它们的节点的细节而运作,只专注于自身的功能。服务的关键方面包括:

    - **作为隔离实例执行**:当用户请求一个服务时,该服务会被发送到某个节点,由该节点将它作为一个隔离进程来运行——根据节点的架构,可能是容器,也可能是虚拟机。这种抽象与**简洁性**原则一致,因为服务不需要感知执行环境。

    - **确定性行为**:服务遵循预先定义的规则,以确保结果的一致性。这与 *Celaut* 对**确定性**的强调相吻合:给定相同的输入,一个服务无论由哪个节点执行,总会产生相同的输出。

    - **分层执行**:*Celaut* 中服务的一个独特之处,在于它们能够通过节点请求执行其他服务(子服务),从而支持复杂的工作流。这映射出了元胞自动机中所见的涌现行为,简单的相互作用会催生出更为精巧的模式。

**协调激励:信誉与支付**

在像 *Celaut* 这样的去中心化系统中,协调不只是技术层面的交互——它同样涉及让所有参与者的激励保持一致,从而确保系统能有效运转。*Celaut* 引入了两种关键机制来实现这种一致性:

- **信誉系统**:
    每个节点与服务都可以基于自己的交互历史建立信誉。节点与服务都有动力维持高标准的可靠性与质量,以此保住自己的信誉。良好的信誉会促使其他节点与用户信任并与之互动,这为公平行事、提供优质服务提供了天然的激励。这种信誉机制在网络内部形成了一种自我调节,参与者都在切身利益的驱使下维护自己的良好声誉。

- **支付机制**:
    除了信誉之外,节点与服务之间的合作还借助支付系统得以促成。当一个节点执行某个服务,或者当服务之间相互交互时,可以以补偿的方式来交换所使用的资源或已完成的任务。这些支付为节点贡献资源、为服务交付价值创造了直接的激励,鼓励整个网络中的协作与公平交换。支付机制确保了资源分配的高效,让节点与服务能够依据各自的优势和能力来运作。

这些机制会在后文详细描述,它们提供了确保 *Celaut* 去中心化方式得以维系的经济框架。正如两个节点之间的通信无需事先就某个具体协议达成一致,这些系统的运作也独立于核心架构之外。这种分离的原因,以及它如何为交互带来灵活性与适应性,会在下文进一步说明。

**连接概念与实践**

*Celaut* 的设计体现了元胞自动机的底层原则:节点与服务层面的简单规则,催生出一个复杂的自适应系统。通过去中心化控制、简化交互并确保确定性行为,*Celaut* 为软件的分发与自动化打造出一个灵活的框架。这让服务得以专注于自身的核心功能,而节点负责编排与分发,从而形成一个能够随着新需求出现而不断适应和扩展的系统。

***Celaut* 的现实影响**

*Celaut* 的架构使得更快速的迭代与实验成为可能,就像在受控环境中运行模拟一样。这让它在需要快速部署和测试新方法的场景中尤为宝贵。凭借现代计算所提供的能力,*Celaut* 能够以前所未有的方式利用这些原则去模拟复杂系统,为提升各行各业的效率与性能开辟新的途径。

这种架构让服务能够专注于自身的功能,而不必操心底层的基础设施。节点则可以高效地管理实例的执行,而不必操心这些实例究竟有什么用处。

## 服务是如何被规范定义的?

*Celaut* 中一个服务的规范由三个主要组件构成:

### 容器 | *BOX*
**BOX** 组件定义了服务运行所依赖的环境,确保服务在不同节点上执行时的一致性。与其他容器化方式不同,*Celaut* 的 BOX 不依赖外部镜像或仓库;相反,它直接指定执行服务所需的完整文件结构。它包含以下细节:

- **架构**:指定服务预期运行的硬件微架构,确保服务与执行节点之间的兼容性。

- **文件系统**:对服务文件结构的完整描述,涵盖服务运行所需的全部文件与目录。这包括二进制文件、库、配置文件以及其他一切必要的资源。
    - **条目分支(Item Branches)** 定义了文件系统的结构,每个分支代表一个文件、一个符号链接,或是一个嵌套的目录结构。
    - 这种方式让整个环境得以自包含,减少对第三方仓库的依赖,并维持**确定性**,因为服务的执行环境无论宿主节点是谁,都始终保持一致。

- **环境变量**:指定服务在运行时可以访问的键值对,让动态配置成为可能,同时无需改动核心文件结构。

- **入口点**:定义服务被执行时启动其主进程的脚本或命令。这确保节点知道该如何正确启动服务。

- **配置(Config)**:包括节点在启动服务时应加载的配置路径与格式。它提供了诸如初始资源分配或特定运行参数之类的必要信息。

- **预期网关(Expected Gateway)**:描述服务如何与 *Celaut* 节点通信,指定它期望从节点得到的协议与方法(网关应用协议)。这个组件确保服务与其宿主环境之间的顺畅通信,把节点当作一个提供系统级交互的操作系统来对待。

BOX 规范让 *Celaut* 服务得以保持可移植、可复现,并且不依赖任何第三方,这与**简洁性**和**确定性**两项原则相一致。

### 接口 | *API*
Celaut 中的 *API*(应用程序编程接口)是一套规则与规范,定义了客户端和其他服务如何与生态系统内的某个服务进行交互。它的主要目的,是为不同的软件组件建立一种清晰、一致的通信方式,确保服务能够以可预测的方式被访问和使用。

通过 *API*,服务用来接收和处理请求的通信协议与端点被明确定义。这确保了任何外部实体,无论是用户还是另一个服务,都可以遵循一套标准化的指令与该服务对接,而无需理解其内部工作原理。

*API* 在 Celaut 中的一个根本性作用体现在去中心化上。通过提供一个定义明确的接口,服务可以自主运作,而不依赖某个中心化的控制器来管理交互。这让整个系统更具可扩展性和韧性,因为每个服务在通信与协作能力上都是自给自足的。

*API* 规范让客户端能够轻松访问和使用服务,同时保持一致的交互方式。它支持 *Celaut* 的**去中心化**原则,让服务能够在通信上自给自足,而无需依赖某个中心化控制器来协商协议。

### 网络 | *NET*
**NET** 组件定义了一个服务可以请求访问和交互的外部网络范围。默认情况下,一个服务与外部网络是隔离的,只能与它的父服务(创建它的客户端)、它的子服务,以及执行它的 *Celaut* 节点通信。这种隔离确保了**确定性**,并通过防止未经授权的数据泄露或交互来增强**安全性**。

不过,有些服务需要访问外部网络才能实现其功能。例如,一个充当比特币节点的服务需要与更广泛的比特币网络交互。为了在不损害安全性的前提下实现这一点,*Celaut* 支持以下方式:

- **受控的外部访问**:服务不会直接访问外部 IP 地址或节点。相反,它会向自己的 *Celaut* 节点发送请求,说明自己需要访问某个特定网络(例如「bitcoin-mainnet」)。*Celaut* 节点会核实该请求,并提供一份该服务可以与之交互的可信对等节点列表。

- **服务请求网络对等节点**:像比特币节点这样的服务,可以通过与自己的 *Celaut* 节点通信来请求额外的资源或网络对等节点。例如,它可能会请求:「我需要来自『bitcoin-mainnet』的对等节点。」节点会评估这个请求,并返回一份经过验证的实例列表(这些实例可能是作为 *Celaut* 网络中服务运行的其他比特币节点)。

- **节点感知与重定向**:如果收到服务请求的 *Celaut* 节点知道自己找不到合适的对等节点(例如它的网络中没有其他比特币节点),它会去寻找一个能够满足这一需求的对等 *Celaut* 节点。这确保了即便最初的 *Celaut* 节点能力有限,服务也总能找到所需的网络连接。

**NET** 组件让 *Celaut* 得以在对外部连接的需求与**安全性**、**确定性**这两项核心价值之间取得平衡,确保服务始终保持隔离,除非被明确允许访问更广泛的网络。

<br><br>

服务的规范定义是 *Celaut* 架构中的关键部分,它让服务能够以一致、可预测的方式被部署和执行。

<br>

节点会从二进制文件中加载服务,并为其提供运行所需的资源。

定义一个服务并没有唯一的方式。
例如,[Proto3 实现](https://github.com/*Celaut*-project/service-lib/blob/master/node-driver/src/node_driver/gateway/protos/*Celaut*.proto#L66) 只是众多可能变体中的一种。

<br>

并非所有节点都会接受一个服务规范的所有可能变体。

>举例来说,节点 A 理解某个特定的 proto3 规范以及一种 JSON 规范。另一个节点 B 理解 JSON 规范以及另一种「JSON + 压缩文件系统」的规范。两个节点之间可以传输它们共同理解的规范所对应的服务,在这个例子中就是 JSON。

## 系统中不同类型的用户角色

作为用户,我们可以在系统中扮演三种角色:

- 节点维护者(类似于在区块链系统中维护一台矿机的人)。
- 服务开发者。这些服务可以被任何人在任意节点(在架构等方面兼容的任意节点)上运行。
- 在节点上启动服务的用户。

因此,维护节点的人(第一类用户)并不关心它究竟是在进行 PoW 挖矿、运行一个交易机器人、分析一段 DNA 序列,还是在做它所运行的服务所做的任何事情。他们只是按照第三类用户的请求执行服务,以换取支付凭证(可以是区块链上的凭证,也可以是任何被接受的支付方式)。开发者(第二类用户)只需要把服务发送给一个或多个节点,这些节点就会负责将服务分发给其他节点,和/或把它上传到一个信誉系统,让用户(或其他服务)知道是否要使用它、何时使用以及为什么使用它。

>这只是对系统的一种简化理解;随着复杂度的增加,可能出现的用户角色种类也会随之增多。

## 追随自然的脚步:数字生态系统

不妨把 *Celaut* 想象成一个数字生态系统,映照着自然界中生物生态系统的动态。在这个类比中:

1. 节点即生物体:*Celaut* 中的节点可以比作自然生态系统中的生物体。每个节点都是一个拥有自身能力与功能的独立实体,就像不同物种占据环境中各自的生态位一样。这些节点相互作用,构成一张类似于生态系统中生命相互关联的网络。

2. 服务即生物功能:*Celaut* 中的服务类似于生物体内的生物功能或过程。每个服务执行一项具体的任务,就像生物体内的器官执行专门的功能一样。正如器官协同运作以维持生命,服务也在节点内部协作,以满足各种各样的计算需求。

3. 去中心化即多样性:*Celaut* 的去中心化原则可以等同于自然生态系统中的生物多样性。在自然界中,生物多样性确保了韧性与适应力,多样的物种为生态系统的稳定与功能做出贡献。同样地,*Celaut* 中的去中心化降低了与单点故障相关的风险,并增强了系统适应变化条件的能力。

4. 效率即能量优化:*Celaut* 中的效率映照着自然系统中所观察到的能量优化。在生物生态系统中,能量沿着食物网流动,生物体优化能量消耗以最大化生存与繁衍的机会。同样地,*Celaut* 优化计算资源,把任务分配到各个节点,以最小化延迟与资源浪费。

5. 简洁性与确定性即自然法则:*Celaut* 中简洁性与确定性的原则,与支配自然系统的底层法则相呼应。正如物理法则支配着宇宙中物质与能量的行为,*Celaut* 的简单规则支配着节点与服务之间的互动。这个确定性的框架确保了一致性与可预测性,类似于受基本法则支配的自然现象所具有的可预测性。

## 信任系统

在 *Celaut* 中,系统的不同部分——节点与服务——彼此并不信任,因此这是一个无需信任的系统。正因如此,一个节点不太可能免费执行服务,一个服务也不太可能在没有依据合约完成支付并收到支付凭证的情况下正常运作(尽管如果它们愿意,当然也可以这样做;就服务而言,这在经济上是可行的,因为它们的边际成本为零)。
<br>然而,要让这些互不信任的部分之间能够互动,就需要合约,也就是(在一个由节点与服务组成的社会中的)社会契约,来传递价值并为每一部分分配信誉。因此,我们(从相对抽象的角度来看)拥有两类系统:支付系统与信誉系统。

> 一个节点可行的策略,是在一开始不进行任何价值交换地提供服务执行,以此提升自己的信誉;等到在他人眼中积累了信誉之后,再开始提高自己的价格。

> 与节点不同,服务的本质是边际成本为零,这意味着它们同时执行的实例数量没有上限(因为执行它们的成本由节点承担),因此很可能许多服务一开始都以零成本运行以积累信誉,在有了信誉之后为了保持竞争力而开始收费,又在不再具备竞争力时回到零成本。


### 支付系统

支付系统让价值能够在 *Celaut* 中的各个实体之间转移。以下是一些可能的类型:

#### 许可智能合约

一套合约系统,允许为服务与节点签发使用许可,其中 Ledger 是就真相达成一致的网络。这样一来,如果 A 想要执行 B 的某个方法,它会先查询自己的合约,执行既定的命令(连接到 Ledger),然后 Ledger 上的合约会签发一份许可,A 会把这份许可发送给 B,以便执行所需的方法。

基于两种不同的分类维度,存在四种截然不同的许可类型。一方面,许可可以是弹性的或静态的;另一方面,可以是交互式的或非交互式的。

- **弹性许可**是指那些可以根据某些参数(请求数量、时间、方法、环境变量等)限制其使用方式的许可。

- **静态许可**是指那些不限制使用的许可。B 知道许可密钥,合约会提供该许可而无法限制其使用。

- **交互式许可**要求 B 连接到 Ledger,以验证所提供许可的有效性。

- **非交互式**许可不要求 B 连接到 Ledger 来验证所提供许可的有效性。

<br>

由此产生了四种许可类型:

- 交互式静态许可(非常直接——用处不大)
- 非交互式静态许可(更适合服务)
- 交互式弹性许可(更适合节点)
- 非交互式弹性许可(相当复杂——用途多样)

<br>

> Ledger 可以是像比特币或 Ergo 这样公开、无需许可的网络,也可以是像 Stripe 这样私有、封闭的平台。唯一的要求是所有参与者都必须支持它们。

<br>


### 信誉系统

信誉系统让用户、节点与服务能够建立一个可据以做出决策的社会生态系统。对节点而言,它们需要知道可以信任哪些对等节点来请求执行服务。
对执行服务的用户而言,信誉系统帮助他们判断哪些服务最适合完成自己想要做的任务。

在 *Celaut* 中,信誉表现为 Ledger 上的记录,代表着一种意见。

就服务而言,它们的确定性本质使得它们的信誉相比节点而言呈现出不同的视角。
很久以前发布的一份信誉证明(一条记录),可能与一份关于该服务的最新证明具有相同的价值(当该服务不与任何网络交互时——这正是服务默认的形态,也就是完全隔离——这一点成立)。
如果它确实与某个网络交互,那么它的信誉就可能取决于它所连接的那些网络的信誉,而这些网络并不具备那种确定性的属性,因为它们会随时间变化。这是因为服务本身并没有改变。

相比之下,节点的信誉则是越新越有价值,因为它的行为可能随时间变化。
当节点彼此接触时,它们会展示各自信誉的证明,而其他节点则可以非共识性地就它们是更可信还是更不可信发表意见。

在信誉系统中,每一个节点、服务或其他类型的参与者,都会在不同程度上信任各种来源,而这些来源又会在不同程度上信任其他来源、节点、服务或实体。因此,当某个参与者面对一个未知实体时,它会查阅自己所信任的来源的意见。

想更具体地了解信誉系统是如何运作的,可以阅读:[Sigma 信誉面板文档](https://github.com/reputation-systems/sigma-reputation-panel/blob/master/README.md)

## 为什么这是必要的

*Celaut* 想要解决的,正是把「*如何解决一个问题*」与「*在哪里、由谁来解决它*」这两件事分离开来。

以一个交易机器人为例。

>交易机器人是根据预先设定的算法,在金融市场中自动执行买卖订单的软件程序。它们之所以重要,是因为可以 7×24 小时运行、快速应对市场变化、并消除情绪偏差,从而提升交易策略的效率与一致性。


<br>

在这样的背景下,如果你现在就想使用一个交易机器人,你可以到网上寻找,并且能够:

1. 寻找一个能替你管理资产组合的网络服务,它有:
    1. 优点:
        1. 你不需要自己运行基础设施。
        2. 你不需要配置任何东西。
    2. 缺点:
        1. 你无法为它建立信誉,因为该网络服务的开发者无法证明系统没有被更改过(例如,
        当一个机器人积累了大量用户之后,他们可能会降低
        它的表现,以此鼓励你使用一个更新的版本)。
        2. 该网络服务的开发者无法向你保证他们没有
        滥用你请求中的数据(在这个例子中,就是
        你资产组合的变动情况)。
2. 寻找一份可以在 GitHub 等平台上找到的源代码,自己在你的电脑上(或云端)运行它。
    1. 优点:
        1. 它是确定性的,意味着(如果它无法连接
        互联网)你可以确信它未来的行为和/或表现不会改变,因为开发者无法修改你此前已经下载的源代码。
        2. 该服务的开发者对你请求的数据没有任何控制权。
    2. 缺点:
        1. 你需要拥有能够运行该代码的设备(基础设施)。
        2. 你需要处理系统配置方面的问题(这些问题往往
        足够棘手,以至于普通用户会转而选择一个网络服务)。

面对这两个选项,*Celaut* 让你能够在不承担它们各自缺点的情况下,同时获得两者的优点。原因如下:



- 基础设施管理是不必要的,因为节点会负责处理它。你不需要去寻找一个云服务商。

- 不需要任何配置。服务的规范涵盖了容器的构建方式、它的架构、它的网络需求以及它的接口。用户完全不需要为这些事情操心。

- 服务开发者无法控制、修改或提取该服务的数据。他们并不控制分发和运行它的那些节点。不过,他们可能会有创建它的动机。
